# ステージ量産分 プレイテスト（2026-10-27）

対象：f2fada4 の時点の main。新しく作られた 1-1〜1-3、2-1〜2-5、3-2、やらかし道場（1-4 friday-push は前回のレビュー済み）
方法：dev サーバーをアプリ内ブラウザで遊んだ。

- 1-1 は、コマンドを手で打って遊んだ。
- ほかのステージは、入力欄に JS でコマンドを流し込んで遊んだ。そのぶん、考える時間が実際に遊ぶより短い。
- 画面幅は 1280×800 で遊び、1024×700 と 1366×768 で並びを測った。

## まとめ

10ステージとも、正解のルートでも罠のルートでも最後まで遊べた。1手目から詰むステージはない。

よかった点：

- **ステージごとに状況の変化（K3）が効いている**。
  - 1-2 の「ついでに CONTRIBUTING も」
  - 2-3 で田中が先に push してくる
  - 3-2 で早瀬先輩が途中で push してくる
- **気づけば、取り返せる（K4）**。
  - 2-1 の Warning のハッシュで救出
  - 2-4 の ORIG_HEAD での救出
  - 2-5 の restore での救出
- **1-1 の推理と 1-2 の隠しの結末が気持ちいい**。1-1 は log の時刻と、田中の「18時には動いてた」を突き合わせる。1-2 は、朝会で部長が自分の書いた文を読み上げる。

直してほしい点：

- **大きな不具合が2つ**。
  - 画面幅 1366px 以下で、中央があふれて右のゴールとチャットを隠す。前回の P1 が、ステージによって再発している。
  - 3-2 で、.env を片づける最後の push が「秘密情報の push（Lv5・4,800万円）」と判定される。
- **遊びの面でいちばん大きいのは、補助のチップが最初から答えを書いてしまうこと**。どのステージでも、`git rm -r --cached 転職`、`git switch -c feature/receipt`、`git pull --no-rebase` などが開始時から並ぶ。チップを順に押すだけで解けてしまい、K5（上手さの余地）が消える。

## 不具合（直してほしい順）

### P1. 中央の列が右の列（ゴール・チャット）の上に重なる。1366px でも起きる

- 外側の grid は `260px minmax(0,1fr) 300px` に直っている。ところが `<main>` 自身の grid（`grid min-h-0 grid-rows-[…]`）に列の指定がない。そのため暗黙の列が中身の最大幅になり、`<main>` の枠をはみ出す。
- いちばん幅を取っているのは、コミットグラフの入れ物（`h-full overflow-auto`）と、4つの領域。
- 測った値：

  | ステージ | 幅 | 中央の実際の幅 | 本来の枠 | 右の列に重なる幅 |
  |---|---|---|---|---|
  | 2-3 矢印 | 1280 | 840px | 720px | 120px |
  | 道場 | 1366 | 926px | 806px | 120px |
  | 道場 | 1024 | 941px | 449px | 492px |

  - 道場の 1024 幅では横スクロールも出て、ローカル・リモートの領域が見えなくなる。
  - 1-1 のようにブランチが1本だけのステージでは起きない。ブランチが増えるステージ（2-3・道場）で起きる。
- 直し方の案：`<main>` に `grid-cols-[minmax(0,1fr)]` を足す（前回の案の、半分がまだ入っていない）。グラフはその中で横スクロールさせる。

### P2. 3-2：.env を片づけた push が「秘密情報の push（Lv5）」になる

- 再現：
  1. `git rm --cached .env` → `git commit --amend --no-edit` → `git push --force`（始末書 Lv4）
  2. 「チェックポイント（push の前）に戻る」
  3. `rm .env` → `git pull --no-rebase` → `git rm --cached .env` → `git commit -m "chore: .env を追跡から外す"` → `git push`
- 結果：3 の push で始末書「鍵をばらまいたことについて」（Lv5、損害額 ¥48,000,000）が出る。部長は「少しお時間よろしいでしょうか」と言い、田中は「早瀬さんのも消えません？」と言う。
- 原因：`src/scenarios/dangers.ts:101-107` は、送ったコミットのファイル一覧（`commitFiles`、そのコミット時点のスナップショット）に .env があれば数える。この push に入るマージコミットは、origin にもともとあった .env をスナップショットに含む。そのため新しく漏らしていないのに数えてしまう。
- 直し方の案：秘密情報のファイルは、push 前の origin（`u.from`）に同じ中身で無かった場合だけ数える。

### P3. 3-2：チェックポイントに戻ると、amend した後の、ほぼ詰んだ状態に戻る

- 「チェックポイント（push の前）」は force push の直前、つまり amend の後の状態。戻った時点の状態は次のとおり。
  - 手元の main：.env を外して作り直したコミット
  - origin：.env 入りの元のコミット＋早瀬先輩のコミット
  - 手元の .env：未追跡のファイルとして残っている
- この状態で `git pull` すると「untracked working tree files would be overwritten」で止まる。抜けるには、.env を消してから pull し、もう一度 rm --cached する必要がある。git として正しい挙動だが、3章の初見のプレイヤーには解けない。しかも、抜けた先で P2 に当たる。
- 直し方の案：このステージのチェックポイントは「履歴を書き換える前」（amend や reset の前）にする。または「やり直す」を勧める。

### P4. 2-4：寝ているはずの田中が、ずっと話す

- 導入では「（すぅ…すぅ…）」と寝ている。それなのに `reset --hard` で「…いま、消えました？」、救出で「あれ？」「…いま、一回消えましたよね？」、クリアで「ありがとうございます」と話す。`kouhai.wake`（「…あれ、先輩まだいたんですか」）は一度も出なかった。
- 直し方の案：このステージの田中のセリフは、起きた後（`kouhai.wake` の後）だけ出す。起きる前の反応は「（寝返りを打った）」のような地の文にする。

### P5. 2-5：restore で戻した後、チップどおりに `git rm --cached 転職` を打つとエラーになる

- `git rm -r 転職`（--cached なし）は、作業ツリーとステージの両方から消す。`git restore --source HEAD 転職` は作業ツリーだけを戻す。そのため次の `git rm --cached 転職` は「pathspec did not match」になる。本物の git でも同じ挙動。
- 困るところ：
  - チップがまだ `git rm -r --cached 転職` を出し続けている。
  - エンジンのヒント「そのファイルは git が知りません。名前のつづりを…」は、この場面では見当違い。
- 直し方の案：
  - 戻した後のヒント（`hint.restoreFile`。演出案の側で書いた文）を「戻したら、そのまま `git commit --amend --no-edit` でいい。コミットからはもう外れてる」にする。
  - チップから rm --cached を外す。
  - 文言は演出案のセッションで直せる。

### P6. 部長のセリフが、実際の操作と合わない（共通のセリフ `src/drama/lines.ts`）

- `boss.danger.BAD_COMMIT_MESSAGE` が「"修正"って、何をだ」に固定されている。道場で `-m "fix"` と打っても「"修正"って」と言う。コミットメッセージを `{message}` で差し込むか、「…何を直した」にする。
- `boss.danger.REPO_DELETED` が「….git ごと消したのか」のまま。点が4つ並んで読みにくい（始末書の bossWord は「…家ごと、か」に直したが、チャットのほうはここにある）。
- `boss.danger.SECRET_PUSHED` が「少しお時間よろしいでしょうか」。3-2 では、失効を依頼しなかったときの結末の決めゼリフと同じ文になっている。最後の結末で初めて出るように、共通のほうは別の文（例：「…キーは、止めたか」）にする。

### P7. 道場：保護された main への `push --force` が「レビューを飛び越えて」に入らない

- `dangers.ts:98` の条件 `!u.forced && protectedBranches.includes(...)` のため、force push だと直接 push として数えない。
- 結果：道場で main に `push --force` したのに、5番の枠が埋まらなかった。force push は保護をいちばん破る操作。
- 直し方の案：`!u.forced` の条件を外す。forced のときも数える。

### P8. 1-2：手数が「4 手（最短 5 手）」と、最短より少なく出る

- `git commit -am` を使うと、add の1手が要らない。par の 5 は add を数えている。
- 直し方の案：par を 4 にする。または、最短を下回ったら「最短より少ない！」と褒める表示にする。

## 使い勝手

- **補助のチップが答えになっている（いちばん大きい）**。開始時から並ぶもの：
  - 1-3：`git switch -c feature/receipt`
  - 2-2：`git fetch`、`git log --oneline origin/feature/coupon`、`git pull --no-rebase`
  - 2-4：`git rm -r --cached node_modules debug.log src/payment/calc.ts.bak`
  - 2-5：`git rm -r --cached 転職`
  - 3-2：`git rm --cached .env`
  - 道場：`git add .env`、`git switch shared`、`git push --force`

  罠（K2）を踏む前に正解が見えてしまう。

  直し方の案：
  - 開始時は status / log / show など「見るコマンド」だけにする。
  - 解き方のコマンドは、ヒントを押した後か、一度間違えた後に出す。
  - 道場はなぞなぞを解く遊びなので、チップを空にする。
- **#dev に、プレイヤー自身の発言が出ない**。1-1 で答えを選んでも、2-2 で報告を選んでも、自分の文がチャットに残らない。先輩の「README で合計は壊れないって」がいきなり出て、何への返事か分かりにくい。選んだ文を、自分の発言として流したい。
- **先輩の助け舟が、もう済んだことを言う**。
  - 1-2：README を直した後に「README.md を開いて、clnoe を直してみ」
  - 2-3：`ls` した後に「ls src/pages で、トップっぽいファイル探してみ」

  idle のセリフを、進み具合（フラグ）で選び分けたい。
- **話し手 system の名前が、地の文にも付く**。
  - 3-2 の「（田中のモニターに、"add の前に status" の付箋が貼られた）」が「検出ボット」の発言になっている。
  - 道場の「称号：歩く障害報告書」が早瀬先輩の発言になっている。

  地の文用に、名前を出さない話し手（narration）を分けたい。
- **同じセリフの連続**。道場で危険を3つ続けると、次の2つが3回ずつ並ぶ。
  - 早瀬先輩「はい、1枚。本番ではやるなよ」
  - 田中「えっ、それ大丈夫なんですか」

  道場の `senpai.newEntry` に言い回しを増やす（演出案の側で書ける）。共通の `kouhai.danger` は、道場では出さない。
- **メニューと見出しで、かっこが二重になる**。「請求書の PDF 出力を push する（余計なものは入れずに）（部長の pull が終わるまで）」。締切の欄に文が入るステージ（2-3「問い合わせが増える前に」、2-5）は、締切のかっこを付けないか、「締切：」と書く。結果画面の「13:05（締切 問い合わせが増える前に）」も同じ。
- **git の出力の順番が、本物と違う**。
  - `switch` の置き去りの Warning：本物は Warning → Switched to branch → Your branch is up to date の順。いまは「Your branch is up to date」が先に出る。
  - `pull`：本物は「From …」が先で、Merge made by … が後。いまは逆。
- **コミットの日付が、現実の時計のまま**。1-2 の amend の出力が「Date: Tue Oct 27 01:21:01」で、作中の月曜 9:57 と合わない。2-4 の「木曜の深夜」とも合わない。作中の時計から日付を作りたい。
- **reset のヒントが、ORIG_HEAD で戻った直後にも出る**。2-4 で `git reset --hard ORIG_HEAD` の後にも「やりすぎたら git reset --hard ORIG_HEAD で戻れます」と出る。このとき ORIG_HEAD は救出の前の位置を指していて、打つとまた消える。ORIG_HEAD を使ったコマンドの後は出さない。
- **1-3：保護されているはずの main に、push が通る**。
  - 現状：GitHub の保護ブランチなら、直接の push は「protected branch hook declined」で弾かれる。このゲームでは通って、始末書になる。
  - 問題：遊びとしては「やらかせる」ほうが面白いが、「保護されていれば弾かれる」ことを学べない。
  - 案：始末書の「なぜまずいか」に「本物の保護ブランチなら、この push は弾かれる。今日は設定が間に合っていなかった」と1文足すだけでもよい。

## 難易度・面白さ

- **1-1** の推理はちょうどいい。
  - 「--oneline だと、誰が書いたか見えないんだ」の気づきが効いている。
  - 選択肢が clone の前から押せるので、当てずっぽうでも解ける。当てずっぽうは「わかりません」より損になるか、確かめたい。
  - README を外したときは先輩が突っ込み、ランクも A に下がった。損になる仕組みはある。
- **2-3** は、速いほうの結末（`ctx.gameSec <= 300`）に届かない。
  - 作中5分でクリアしないと出ないが、par の5手と、避けられない push の拒否だけで作中3分かかる（成功30秒×4、エラー60秒）。
  - 残りは実時間でおよそ1分。ファイルを探して印を消すには足りない。
  - 私は JS でコマンドを流しても作中 13:05 で、遅いほうの結末だった。
  - 速い結末の境目を作中8分くらいにするか、エラーの時間を30秒にする。
- **2-1・2-2・1-2** は、締切の数分前のクリアになった（14:56、11:55、09:57）。緊張感は出ているが、初見でヒントを2回押すと間に合わない。時間制限なしを選べるので、問題はない。
- **1-3** で、部長の「レビュー会、14:20 からにする」（状況の変化）は見られなかった。早く終わると出ないのだと思う。K3 として毎回見せたいなら、2手目のあとなどに出す。
- **2-5** の救出と結末の出し分けは、気持ちよく遊べた。--cached のありがたみが分かる。チップさえ答えを出さなければ、いちばんいいステージになる。
- **3-2** で、失効の依頼を最初にやれば最短で解ける流れは分かりやすい（「git のコマンドの前に、#dev でできることもあります」の案内が効いている）。一方、失敗した後の取り返しは P2・P3 のせいで、いまは罰ゲームになっている。
- **道場** の役満と称号の上がり方は楽しい。3手で「歩く障害報告書」になり、損害額が跳ねる。「道場を元に戻す」で、図鑑を残したまま戻せるのもいい。
- **4つの領域の「リモート」が fetch の前から「サーバーに新しい更新」と出る**。
  - 道場で見た。2-2 でも同じなら、「fetch するまで手元の記録は古い」という教えと食い違う（ターミナルは「up to date」と言い、図は「新しい更新」と言う）。
  - 案：図は手元の origin/… の記録だけで描く。本物の origin は fetch した後に出す。

## 確かめていないこと

- 1024 幅での遊び（並びを測っただけ）。
- 各ステージで、ほかの結末に分かれるか。次のものは見ていない。
  - 2-2 の報告 B〜D
  - 2-4 の memo.txt と、ゴミごと push
  - 2-5 の流出と、amend 後の隠しの結末
  - 3-2 の失効なし
- 道場の残り6枠（印・迷子・直接 push・共有ブランチ・鍵・書きかけ）と、10枠でのクリア。
- 時間制限なしのモードと、締切を過ぎたときの演出。
- 手で打ったときの細かい操作感（1-1 以外）。JS で入力を流し込んだので、Tab 補完と ↑↓ の履歴は見ていない。
