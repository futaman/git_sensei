# シナリオモード プレイテスト（2026-10-26）

対象：ストーリー「金曜17:45、定時前の push」（`src/scenarios/friday-push/`、`src/ui/stage/`。M4 の未コミット作業）
方法：dev サーバーをブラウザで実際に遊んだ。画面幅 1280×800 と 1024×700。

| 回 | やったこと | 結果 |
|---|---|---|
| 1 | 正解の手順（push → pull → 手で解消 → add → commit → push） | S（5手、17:57） |
| 2 | 「自分の変更を採用」→ そのまま push → 直すコミット（`-am "修正"`）→ push。時間制限なし | A（7手、始末書1） |
| 3 | `git push --force` → チェックポイントに戻る → ヒント連打で 18:00 を過ぎる | 締切後も続行できた |
| 4 | 印を残したままコミット、`&&` でつなぐ | 始末書 Lv2 |

## まとめ

遊びの骨格はよくできている。push が拒否され、pull でぶつかり、「採用」ボタンの罠で片方が消え、直すコミットで取り返す。この流れが、セリフとゴールのチェックでちゃんと体感できる。force push の始末書とチェックポイントへの戻りも分かりやすい。
一方で、**画面幅 1366px 以下でゴールとチャットが隠れるレイアウトの不具合**がある。ほかに、**セリフが状況と合わない不具合**が3つ、**時間制限なしの結果表示の誤り**、**始末書の文面がない**不具合がある。どれも遊んだ人がすぐ気づく。

## 不具合（直してほしい順）

### P1. 中央の列があふれて、右のゴール・チャットの上に重なる（幅 1280px 以下で再現）

- `StageScreen.tsx:98` の `<main className="grid …">` に列の指定がない。そのため暗黙の列が中身（4つの領域の図、最小 857px）の幅になり、720px の枠からあふれる。
- 1280×800：右の列（ゴール・チャット）の左端が中央の白い面に隠れ、文が途中で切れる。
- 1024×700：ゴールの欄が完全に隠れ、ページ全体に横スクロールバーが出る。
- ノート PC の多くが 1280〜1366px なので、多くの人がこの状態で遊ぶことになる。
- 直し方の案：
  - `<main>` に `grid-cols-[minmax(0,1fr)]` を足す。
  - 4つの領域を `overflow-x-auto` にするか、狭い幅では縦に並べる。
  - あわせて、狭い幅で右の列をたたむ。

### P2. 後輩（田中）のセリフが、どの失敗にも force push 用の文言になる

- `lines.ja.ts` は汎用の key を上書きしている。
  - `kouhai.danger` →「…先輩、いま --force って…」
  - `kouhai.error` →「えっ、弾かれました？」
- 汎用の key なので、別の失敗でもこの文言が出る。実際に出たのは次の場面。
  - コミットメッセージ「修正」：「いま --force って…」
  - 印を残したコミット：「いま --force って…」
  - `git commit` のエラー：「えっ、弾かれました？」
- 直し方の案：
  - 危険の種類ごとに key を分ける（`kouhai.danger.FORCE_PUSH_OVERWROTE` など。上司はすでにそうなっている）。
  - 汎用の key は汎用の文言のままにする。

### P3. 始末書が1枚でもあると、結末が「押し切るなって言ったろ」になり、取り返したときのセリフも消える

- `drama/engine.ts:352-361` の `finish()` は、`reports.length > 0` なら一律で `ending.afterReport` を出し、`epilogue` を出さない。
- 実際の流れ：
  1. 2回目で「修正」の始末書（Lv1）が出た。
  2. 0.036 を消したままコミットし、直すコミットで取り返した。
  3. それでも先輩は「な？ 押し切るなって言ったろ」と言った。
  4. 本来出るはずの「消さずに、直すコミットを足す。それで合ってる」と「一回消えたときは焦りましたけど…」は出なかった。
- このステージでいちばん伝えたい「直すコミットで取り返す」の褒め言葉が、軽い始末書1枚で消えてしまう。
- 直し方の案：
  - `ending.afterReport` は、force push の始末書があるときだけ出す。
  - `epilogue` は、始末書があっても出す。

### P4. 時間制限なしでクリアすると、間に合っていても「（締切には間に合わなかった）」と出る

- `drama/engine.ts:363` の `const slow = this.settings.untimed` が原因。結果画面（`Overlays.tsx:281`）は、`slow` をそのまま「間に合わなかった」と表示している。
- 実際：17:56 にクリアしたのに表示された。
- 直し方の案：
  - 時間制限なしなら「（時間制限なし）」と出す。
  - または `slow` を「締切を過ぎた」の意味に限る。

### P5. このステージで文面のない始末書が出ると、中身が `BAD_COMMIT_MESSAGE` だけになる

- `git commit -am "修正"` で始末書（Lv1）が出た。題も本文も、内部の名前 `BAD_COMMIT_MESSAGE` だけだった。
- `REPORTS` に文面があるのは2種類だけで、`Overlays.tsx:153,169` は文面がないと kind をそのまま出す。
- 直し方の案（どちらか）：
  - 危険の全種類に既定の文面を用意する（`drama/` 側に共通のものを置き、シナリオが上書きする）。
  - 文面のない Lv1 は始末書にせず、上司のひと言だけにする。

### P6. 先輩の「手が止まったとき」のセリフが、いまの状態と合わない

- `senpai.idle` は、言った回数で順に進む。
  1. 「pull して、ぶつかったところを見てみ」
  2. 「<<<<<<< と >>>>>>> の間…」
  3. 「上の段と下の段から…」
- 1回目は、push もしていない最初の 20 秒で「pull して」と言われた（push の拒否を体験する前に答えを聞くことになる）。
- 2回目は、まだコンフリクトしていないのに「<<<<<<< と >>>>>>> の間…」と言われた。
- `helper()` は、間違えた後以外では `undefined` を返すので、ふつうの状態でも段階ごとの言い分けになっていない。
- 直し方の案：`helper()` が、すべての phase で状態に合う key を返す（beforePush なら「とりあえず push してみ」など、ヒントの弱い版）。

### P7. 想定どおりの1手目（push が拒否される）で、後輩の信頼が −3 される

- 解答手順（par 5）の1手目は、拒否される push。でも拒否は「エラー」として数えられ、`trust.delta.error` が引かれる。結果、毎回まなざしが下がる。
- ステージの説明は「push が弾かれても」と、拒否を前提にしている。だから、ここで引くのは理屈に合わない。
- 直し方の案：シナリオが「想定内のエラー」（このステージでは最初の PUSH_REJECTED）を指定できるようにし、減点しない。

## 使い勝手（直すと良くなる）

- **エディタが狭い**
  - 左の列 260px × 約 280px に CodeMirror があり、`export function calcFee(amount: number)` が折り返す。
  - このステージは「手で直す」のが正解なので、いちばん大事な作業場所がいちばん狭い。
  - 案：コンフリクトのある間はエディタを広げる（中央のグラフと入れ替える、など）。
- **「採用」ボタンの罠に説明がない**
  - このステージでは「自分の変更を採用」と「取り込む変更を採用」の、どちらを押しても片方が消える。罠として正しいが、失敗の後に「両方残すには手で直す」という案内はない。
  - 先輩の助け舟が出るまで、待つしかない。
  - 案：`kouhai.lostRate` の直後に、先輩の `hint.redo` 相当（タダの弱い版）を出す。
- **ヒントの罰が二重**
  - ヒント1回で、時計が −2分、後輩の信頼が −5 になる。
  - 連打しても同じ文が繰り返されるだけ。
  - 初学者がヒントを避けるようになるので、どちらか一方にするのがよい。
- **`&&` が使えないのに、エラーが分かりにくい**
  - `git add . && git commit -m wip` → `error: unknown switch 'm'` と出る。
  - 実務の癖で打つ人は多い。
  - 案：`&&` と `;` を見つけたら「このターミナルでは1行に1コマンドです」と出す（または順に実行する）。
- **途中で抜けると、確認なしで消える**
  - 「メニューへ」は確認なしで、ステージの進み具合が消える（「やり直す」には確認がある）。
  - リロードでも消える。
  - 5分のステージなので保存までは要らないが、「メニューへ」には確認がほしい。
- **クリアの記録が残らない**
  - S でクリアしても、メニューに何も残らない（ランク・クリア済みの印）。
  - 繰り返し遊ぶ動機が弱い。
- **ゴール2が最初から ✓**
  - 「田中さんの修正を消さない」は守りのゴールなので、最初から達成になっている。
  - 始めた瞬間に1つ ✓ がついていて、「もう何かした？」と戸惑う。失敗すると ✓ が外れる。
  - 案：守りのゴールは見た目を変える（例：「🛡 守る」として、外れたときだけ赤くする）。
- **リモートの欄が先に答えを言う**
  - 4つの領域の「リモート」に「サーバーに新しい更新」と出る。fetch していないので、手元の git は知らないはずの情報。
  - push の拒否で気づく体験を先取りしてしまう。
  - 案：fetch・pull するまでは出さない。
- **pull の出力の順番**
  - `From /srv/git/payment-app` が CONFLICT の後に出る（本物は最初）。stdout と stderr を出す順の問題と思われる。
- **メニューのステージカードがボタンではない**
  - アクセシビリティの木では `generic` になっていて、Tab で選べない可能性がある。
  - ファイル一覧の各行も同じ。

## 難易度・面白さ

- **難易度**：git の操作自体はやさしい（par 5）。難しいのは「狭いエディタで、印を消して1行ずつ拾う」作業。
  - 時間は、作中15分＝実時間5分。慣れた人で2〜3分、初学者は手で直すのに手間取ると、ぎりぎりになる。
  - 「時間制限なし」があるので、厳しすぎることはない。
  - 締切を過ぎてもすぐには終わらず、上司の機嫌が 10秒ごとに −2 になる。雷までは確かめていない。
- **面白さ**：
  - 「採用」ボタンの罠 →「あれ…僕の 0.036 が…」→ 直すコミットで取り返す、という流れがいちばん面白い。間違えても先に進めるので、学びとして強い。
  - force push の始末書とチェックポイントも、怒られる体験として効いている。
  - P2・P3 のセリフのずれは、この演出の良さを直接こわすので、優先して直してほしい。
