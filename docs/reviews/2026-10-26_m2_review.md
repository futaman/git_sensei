## 1. 不具合

### B1【致命】Object.prototype と同じ名前のファイルで、アプリが永久に開けなくなる

**再現手順**
1. 「＋ 新規ファイル」を押し、`toString` と入力して Enter
2. 画面が真っ白になる（コンソール：`TypeError: (config.doc || "").split is not a function` at `Editor.tsx`）
3. リロードしても真っ白のまま。「最初からやり直す」ボタンも消えているので、**利用者には直す方法がない**（開発者ツールで localStorage を消すしかない）

`constructor`, `valueOf`, `hasOwnProperty`, `__proto__` なども同じ。

**原因**
`Record<string, …>` に対して `in` 演算子や `obj[key]` で調べているため、プロトタイプのプロパティが「ある」と判定される。
- [freeMode.ts:158](../../src/ui/store/freeMode.ts) `path in ws.files` → `'toString' in {}` は true なので、ファイルを作らずに選択だけする
- [FreeModeScreen.tsx:25](../../src/ui/play/FreeModeScreen.tsx) `ws.files['toString']` は関数 → それを CodeMirror に渡して落ちる

エンジン側にも同じ型の問題がある（Node で再現）：
- `toString` を `git add` → 作業ツリーから削除 → `fileStates()` / `git status` / `git commit -a` が `TypeError: string expected` で落ちる。`ws.files['toString']` が関数なので「削除済み」と判定されず、関数を SHA-1 にかけている（[status.ts:32-34](../../src/engine/worktree/status.ts)、[commit.ts:59](../../src/engine/commands/commit.ts)、[checkout.ts:31](../../src/engine/worktree/checkout.ts)）
- 同じ箇所：`p in git.index`、`ref in git.refs`、`oid in git.objects`、`GIT_COMMANDS[sub]`（[index.ts:137](../../src/engine/index.ts)）

**修正案**
- `in` と `obj[key]` での存在確認を、すべて `Object.hasOwn(obj, key)` に置き換える。値を読むときも `Object.hasOwn` で確かめてから読む小さな関数（例 `own(obj, key)`）を用意して統一する
- `GIT_COMMANDS` / `OPTIONS` などの表も同じ（または `Map` にする）
- Biome の `noRestrictedSyntax` などで、engine 内の `in` 演算子を禁止できるか検討する

**受け入れ条件**
- `toString`, `constructor`, `__proto__`, `valueOf`, `hasOwnProperty` の各名前で「作成 → 編集 → add → commit → 作業ツリーから削除 → status → commit -a → switch」が通り、本物の git と同じ結果になる（突き合わせテストに1ケース追加）

### B2【致命】描画中の例外でアプリ全体が消え、壊れた状態が保存され続ける

B1 は入口の1つにすぎない。今後コマンドが増えると、`fileStates()` / `repoView()` / CodeMirror の中で例外が出る経路は必ずまた見つかる。そのたびに**保存データごと壊れて復旧できない**のが本当の問題。

**修正案**
1. ルートに **ErrorBoundary** を置く。例外を受け止めたら「表示中にエラーが起きました」と「保存データを消してやり直す」ボタンを出す（ボタンで `localStorage.removeItem('git-sensei:free-mode')` → リロード）
2. 保存データを読み込むとき（persist の `onRehydrateStorage` か `merge`）に、`fileStates()` と `repoView()` を試しに実行する。例外が出たら保存データを捨てて初期状態で始める
3. 1 と 2 のテストを書く（壊れた保存データを入れて起動しても、白い画面にならない）

### B3【高】エンジン内の想定外の例外で、コマンドが無反応になる

**再現**
- `git add "["` / `git add "a[b"` → `SyntaxError: Invalid regular expression`（[pathspec.ts:18](../../src/engine/worktree/pathspec.ts)。`[` を正規表現に素通ししている）
- `git hasOwnProperty` / `git valueOf` / `git __proto__` → `TypeError`（B1 と同じ原因）
- 画面では、出力が何も出ず、入力欄も消えないまま固まったように見える（[freeMode.ts:134](../../src/ui/store/freeMode.ts) の `execute` を try/catch していない）

本物の git では `git add "["` は `fatal: pathspec '[' did not match any files`（終了コード 128）。

**修正案**
- pathspec：`[...]` を正しく文字クラスとして変換する。閉じていない `[` は文字そのものとして扱う（本物の git と同じ）。正規表現を組み立てる前に、`]` を含むすべての記号をエスケープする
- `execute()` の一番外側で、`Exit` 以外の例外も受け止める。world は変えずに `git-sensei: 内部エラーが起きました（〇〇）` と出し、終了コード 1 を返す。**利用者の入力で throw されることは決してない**、をエンジンの約束にする
- 上記を守るための property テスト（ランダムな記号列を `git add` / `switch` / `log` に入れても throw しない）があると安心

### B4【中】今いるブランチへの `branch -M` が通ってしまう

**再現**（main にいて、x は main より古いコミットを指している）
```
git branch -M x main
```
- シミュレータ：成功する。main が x のコミットに移るのに、index と作業ツリーはそのまま → 存在しない「ステージ済みの変更」が出る
- 本物の git：`fatal: cannot force update the branch 'main' checked out at '...'`（終了コード 128）

**修正**：[branch.ts:135](../../src/engine/commands/branch.ts) の `renameBranch` で、上書き先が今いるブランチなら `createBranch` と同じエラーにする。突き合わせテストを追加する。

### B5【中】ファイルとディレクトリの名前がぶつかる

**再現**：「新規ファイル」で `d` と `d/x` を両方作る → `git add .` → `git commit`
→ 同じ名前 `d` を、ファイルとディレクトリの両方として持つ tree ができる（本物の git では作れない。`git fsck` でエラーになる形）。ハッシュも本物とずれる。

**修正**：
- [FilePanel.tsx:30](../../src/ui/components/files/FilePanel.tsx)（と今後の `touch` / `mkdir`）で、途中のパスがファイルのとき、または作ろうとしたパスがディレクトリのときは「同じ名前のファイル（フォルダ）があります」と出して作らない
- `switch` / `merge` で、移動先の tree が作業ツリーとファイル・ディレクトリの関係でぶつかるときの扱いも決めておく（M5 の reset/restore の前に）

### B6【低】`constructor` などが未追跡として表示されない
B1 の修正で直るはず。受け入れ条件に含める。

### B7【低】`git log -n -1`
本物の git は負の数を「無制限」と扱う。いまは `slice(0, -1)` で最後の1件が消える（[log.ts:55-57](../../src/engine/commands/log.ts)）。

### B8【低】性能と保存
- 8000行のファイルを全部書き換えて `commit -a` すると約0.5秒かかった（差分の行数を LCS（O(n·m)）で数えているため）。行数が増えると、その間画面が固まる
- `abbrev()` が毎回すべてのオブジェクトを調べるので、`repoView()` は「コミット数 × オブジェクト数」になる
- docs/04_spec_scenarios の「本日26時リリース」は node_modules 12,483ファイル＋48MB の debug.log を想定している。**今のデータ構造（全オブジェクトを1つのオブジェクトに持ち、まるごと localStorage に保存する）では扱えない**。M3 の前に方針を決めてほしい（例：巨大なファイルは「サイズだけ持つ疑似blob」にする、保存は IndexedDB か保存しない、差分は Myers 法にする）
- localStorage の容量（約5MB）を超えると、保存の失敗は `safeStorage` で黙って無視される。少なくとも「保存できませんでした」を一度だけ表示したい

## 2. セキュリティ

**結論：いま悪用できる穴は見つからなかった。** バックエンドも外部への通信もなく、出力はすべて React のエスケープを通っている（`dangerouslySetInnerHTML`・`eval`・`new Function` は使っていない）。突き合わせテストの実行部（[realGit.ts](../../tests/golden/realGit.ts)）も、`spawnSync` に引数を配列で渡していて、シェルを通さず、HOME と git の設定も一時ディレクトリに分けている。良い作り。

配信前に入れておいてほしいもの：

| ID  | 内容                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | **プロトタイプ汚染の芽**：B1 の `in` / `obj[key]` は、いまは各オブジェクトの中だけで壊れる（グローバルな `Object.prototype` は汚染されないことを確認した）。ただ、今後 `git config` や設定の読み込みで「利用者の入力をキーにして入れ子のオブジェクトに書き込む」と汚染につながる。B1 の修正で `Object.hasOwn` に統一しておけば予防になる |
| S2  | **正規表現の DoS**：pathspec の `*` を `.*` に変えているので、`git add "*a*a*a*a*a*a*a*a*b"` のような入力で長いパスに対して遅くなりうる。被害は自分のタブだけなので低い。B3 の修正のときに、glob を正規表現を使わずに照合するか、`*` の数に上限を設ける |
| S3  | **配信の設定**（Cloudflare Pages）：`public/_headers` に `Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`frame-ancestors 'none'` を入れる。外部のスクリプトを使っていない今のうちに入れるのが一番楽 |
| S4  | **CI**：[ci.yml](../../.github/workflows/ci.yml) に `permissions: contents: read` を書く（既定のトークンの権限を絞る）。アクションはタグ（`@v5`）ではなくコミットSHAで固定するのが望ましい |

将来の注意（いま直す必要はない）：
- docs/04 §8.3 のリプレイを**URLやファイルで共有**するようになったら、読み込むデータは信用しない（スキーマで検証してから使う）
- `git config user.email` を打てるようになると、利用者が本物のメールアドレスを入れて localStorage に残る。共有機能を作るときは中身に含めない

## 3. ゲームとしての評価（難易度・面白さ）

いま遊べるのはフリーモードだけなので、**現在の手触り**と、**仕様書（docs/04 の2つ）の設計**に分けて評価する。

### 3.1 フリーモード（いまの状態）

良い点
- `init → add → commit → switch -c` まで迷わず進めた。補助チップ（`git commit -m ""` でカーソルが引用符の中に入る）とできごと欄の日本語の説明がわかりやすい
- コミットグラフ、4領域、ファイルの印（U/M/D）が、コマンドを打つたびに同時に変わるので「何が起きたか」が目で追える。学習ツールとしての土台はしっかりしている
- 未対応のコマンドに「未対応」とはっきり出す方針（docs/03 §1.3）は、嘘を教えないので良い

物足りない点
- **目標がないので、遊ぶ理由がない**。サンドボックスとしては良いが、5分ほどで手が止まる。M4 を待たずに、フリーモードにも「小さなお題」（例：ブランチを作って1コミットしてmainに戻る）を3〜5個置くだけで、遊びの手触りがかなり変わる
- 1手戻す（undo）がない。初心者は「壊したら全部やり直し」が怖くて試せない。docs/05 で Zustand の履歴を使った undo に触れているので、フリーモードに入れてほしい
- 幅 800px では4領域の文字が切れる（PC優先なので後回しでよい）

### 3.2 仕様の設計（docs/04_spec_drama_system・docs/04_spec_scenarios）

**面白さ：コンセプトは強い。** 「わざとやらかさせる」「始末書図鑑を集める」「部長が怒るほど口数が減って敬語になる」は、競合にない明確な売りになる。ヤバ度を「ミスの重さ × どこまで広がったか」で決め、NPC が pull するまでのレースにする設計も、git の怖さ（push したら戻せない）を体で覚えさせる良い仕組み。

**難易度：このままだと初心者には厳しすぎる。** 気になった点を優先度順に挙げる。

| #   | 問題                                                                                                                                                                                                                                                                  | 提案                                                                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 3.3 総評

- **学習ツールとしての土台（エンジンの正確さと可視化）は高品質**。本物の git とハッシュまで一致させる突き合わせテストは、この種のアプリでは珍しいほど丁寧
- **ゲームとしての面白さは、まだ仕様の中にしかない**。コンセプトは強いが、難易度の曲線と罰の強さを調整しないと、狙っている初心者が序盤で離れる
- 次に効くのは「フリーモードの小さなお題＋undo」と「章の難易度曲線を決めること」
