# 仕様：演出システム（後輩の信頼・上司の機嫌・無駄操作の判定）

ステータス：**確定（数値は仮。遊んでから調整する）**／2026-10-25

> **担当範囲**：この文書が決めるのは**仕組み**だけ。
> - ゲージの計算
> - 操作の分類（無駄操作の判定）
> - 危険イベントの重さ
> - 演出キューの形式
>
> **演出の中身**（キャラクター、セリフ、表情、カットインの見せ方、始末書の文面など）は**別のセッションで考案中**。この文書に出てくるセリフや表現の例はすべて**仮**で、そちらの案で差し替える。
> 両者の境界は §7 の `Cue`（演出キュー）。演出側は `Cue` を受け取って表示するだけにする。

## 0. 全体の流れ

```
コマンド入力
  ↓
gitエンジン execute() → { world', output, events[] }   ← 02で決めた意味イベント
  ↓
操作の分類（Classifier）……「このコマンドは前進か、無駄か、後退か、危険か」を決める
  ↓
演出エンジン（Drama）
  ├─ 後輩の信頼を更新 → 表情・つぶやき
  ├─ 上司の機嫌を更新 → 小言／説教／激怒カットイン
  └─ 作中の時計を進める
  ↓
演出キュー → チャット投稿、アイコンの差し替え、カットイン、画面の揺れ
```

- gitエンジンは演出のことを知らない。演出エンジンは `events` と状態の差分だけを見る
- 判定はすべて決定的に行う。入力は「コマンド列＋各コマンドの実行時刻」とする（§8）。同じ入力なら同じ演出になり、リプレイで再現できる

## 1. 演出の基本方針

1. **上司の怒りは技術的に必ず正しい。** 理不尽に怒らず、人格も否定しない。怒る内容がそのまま学びになる
2. **怒られた後には必ず「なぜダメ？」がある。** チャットのボタンから解説と正しい戻し方を読める
3. **確認するのは良いこと。** `status` や `log` で状態を見ても減点しない。後輩は「ちゃんと確認するんだ…」と感心する
4. **実時間で緊張感を出す。** 作中の時計は実時間で進み、期限もある（§8）。ただし設定で「時間制限なし」を選べるようにし、初心者が焦って学べなくなることを防ぐ

## 2. 操作の分類（無駄操作の判定ロジック）

### 2.1 分類の種類

各コマンドの実行後、次の**上から順に**判定し、最初に当てはまったものを採用する。

| #   | 分類       | 判定条件                                                               | 例                                                           |
| --- | ---------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| 1   | **危険**   | 危険イベントが出た（§4）。ただし今のシナリオで許可されているものは除く | 共有ブランチへの `push --force`                              |
| 2   | **エラー** | コマンドが失敗した                                                     | 存在しないブランチに `switch` する                           |
| 3   | **観測**   | 状態を見るだけのコマンド                                               | status, log, diff, show, `branch`（一覧表示）, reflog, `cat` |
| 4   | **前進**   | このシナリオのマイルストーンを新たに満たした                           | `.env` を追跡対象から外した                                  |
| 5   | **後退**   | 意味のある状態が、このシナリオ中に一度通った状態に戻った               | `add` してすぐ `restore --staged` した                       |
| 6   | **空振り** | 意味のある状態がまったく変わらなかった                                 | main にいるのに `switch main`                                |
| 7   | **通常**   | 上のどれでもない。必要な途中の手順かもしれないので、減点しない         | ブランチを作る                                               |

### 2.2 「意味のある状態」のハッシュ

後退と空振りは、**状態のハッシュ値**を比べて自動で判定する。シナリオごとに書く必要がない。

ハッシュに含めるもの：
- 全リポジトリの refs、HEAD、index、作業ツリー、stash
- 各リモートの追跡ブランチ

ハッシュから除くもの：
- reflog（毎回必ず変わるため）
- オブジェクトの保存領域（増える一方なので、戻ったことにならない）
- 作中の時計

シナリオの開始時から、通った状態のハッシュを `visited: Set` に記録していく。

> 後退でも「正しいやり直し」のことがある。たとえば、間違えたcommitを `reset --soft HEAD~1` で取り消すのは良い判断。
> そこで、**直前の自分の操作がエラーか危険だった場合、それを打ち消すのは後退にしない**（ミスにすぐ気づいたと見なし、少し加点する）。

### 2.3 観測コマンドの扱い

- 状態が変わった後の最初の観測：**±0**
- 危険な操作の直前に観測していた：**+3**（「確認してから実行する人だ…」）
- 状態が変わらないまま同じ観測を**3回以上**続けた：3回目から **−2**（後輩「…先輩、迷ってます？」）

### 2.4 手数と評価ランク

- **手数**：観測以外のコマンドの数（観測は数えない）
- **基準手数（par）**：シナリオの作者が決める最短の手数。作者が用意した解答手順は、本物のgitとの突き合わせテストにも通す
- **スマート解**：作者が登録した「より良い書き方」を使うと加点する
  - `--force` ではなく `--force-with-lease`
  - `branch` と `switch` を別々に打たず `switch -c`
  - `log` ではなく `log --oneline --graph`

| ランク | 条件                                  | 後輩の反応                                                                |
| ------ | ------------------------------------- | ------------------------------------------------------------------------- |
| S      | 手数 ≤ par、危険0、信頼85以上、期限内 | カットイン「先輩…一生ついていきます！！」                                 |
| A      | 手数 ≤ par+2                          | 「さすがです！」                                                          |
| B      | 手数 ≤ par+5                          | 「ありがとうございます…」（普通）                                         |
| C      | それより多い                          | 「…助かりました（小声）」                                                 |
| D      | 最後の信頼が25未満                    | 解決はしたが、チャットに「田中さんが #help に質問を投稿しました」と流れる |

## 3. 後輩の信頼ゲージ

### 3.1 値と表情

- 範囲は0〜100。開始値はシナリオで決める（標準は80）
- 後輩が見ているシーン（主に後半の章）だけ有効になる

| 段階 | 範囲    | アイコン   | まなざし                        |
| ---- | ------- | ---------- | ------------------------------- |
| 憧れ | 85〜100 | キラキラ   | 「先輩すごい…」                 |
| 期待 | 65〜84  | まっすぐ   | 普通に見守る                    |
| 不安 | 45〜64  | 眉が下がる | 「大丈夫かな…」                 |
| 疑心 | 25〜44  | 目が細い   | 「この人、本当にわかってる…？」 |
| 虚無 | 0〜24   | 光のない目 | 「…」（何も言わなくなる）       |
- **表情がちらつかないようにする**：段階の境目をまたいでも、3ポイント以上離れるまで表情は変えない
- 表情は段階が上がったときと下がったときで違うアニメにする（下がるときはゆっくり暗くなる）

### 3.2 増減の表

| 分類・行動               | 増減                              | 後輩のつぶやき（例）                 |
| ------------------------ | --------------------------------- | ------------------------------------ |
| 前進（マイルストーン）   | +5                                | 「おお…」                            |
| スマート解               | +8                                | 「そのオプション知らなかったです！」 |
| ミスをすぐに打ち消した   | +2                                | 「（あ、すぐ直した）」               |
| 危険な操作の前に観測した | +3                                | 「確認してから実行するんですね」     |
| 通常                     | 0                                 | —                                    |
| 空振り                   | −4                                | 「…？」                              |
| 後退                     | −6                                | 「先輩、それさっきも…」              |
| エラー                   | −3, −6, −9…（連続するほど増える） | 「えっ」「また…？」                  |
| 観測の空回り（3回目〜）  | −2                                | 「…迷ってます？」                    |
| ヒントを見る（後半の章） | −5                                | 「（先輩もヒント見るんだ…）」        |
| 手が止まる（§8.2）       | 45秒から30秒ごとに −2             | 「…」「（入力中…）」                 |
| 危険                     | −15                               | 「えっ、それ大丈夫なんですか！？」   |
- つぶやきは**候補からランダムに選ぶ**（シード固定で再現可能）。直前と同じセリフは出さない
- 同じ分類が連続すると、セリフが**段階的にきつくなる**
  - 例：後退1回目「あれ？」→ 2回目「先輩、それさっきも…」→ 3回目「（入力中…）」と表示されては消える

## 4. 上司の機嫌

### 4.1 値と反応

- 範囲は0〜100。標準の開始値は50（もともと不機嫌）
- 機嫌は、シナリオの結果と作中時間の経過で上下する。機嫌が上がることはめったにない

| 状態           | 範囲   | 表現                                                                           |
| -------------- | ------ | ------------------------------------------------------------------------------ |
| 上機嫌（レア） | 80〜   | 「…まあ、悪くない」（照れ隠し）                                                |
| 普通           | 40〜79 | 黙っている                                                                     |
| 不機嫌         | 15〜39 | 小言が増える                                                                   |
| 爆発寸前       | 1〜14  | アイコンが震える                                                               |
| **雷**         | 0      | 全画面カットイン＋画面の揺れ。**始末書**をもらい、チェックポイントからやり直し |

### 4.2 危険イベントの重さ

| 重さ | イベント                                                                | 機嫌                    | 演出                           |
| ---- | ----------------------------------------------------------------------- | ----------------------- | ------------------------------ |
| 致命 | `SECRET_PUSHED`（秘密情報をpush）                                       | −50                     | 激怒カットイン                 |
| 致命 | `FORCE_PUSH_OVERWROTE`（他人のコミットを消した）                        | −45                     | 激怒カットイン                 |
| 致命 | `UNCOMMITTED_CHANGES_DISCARDED`（まだpushしていない自分の作業を消した） | −30                     | 激怒カットイン＋後輩も青ざめる |
| 重大 | `DIRECT_PUSH_TO_PROTECTED`（mainに直接push）                            | −25                     | 説教（長文）                   |
| 重大 | `HISTORY_REWRITTEN_ON_SHARED_BRANCH`（共有ブランチの履歴を書き換え）    | −20                     | 説教                           |
| 軽微 | 質の低いコミットメッセージ（`aaa`, `修正`, `test`, `wip`）              | −5                      | 小言「"修正"って何をだ」       |
| 軽微 | `git add .` で不要なファイルが混ざった（node_modules など）             | −5                      | 小言                           |
| 軽微 | 1つのコミットに大量の変更                                               | −3                      | 小言                           |
| 加点 | チャットで事前に報告・相談した（シナリオで用意した選択肢）              | +10                     | 「…報告は早いな」              |
| 加点 | 期限より早く解決した                                                    | 残り時間に応じて +5〜15 | —                              |
| 時間 | 期限を過ぎた                                                            | 10秒ごとに −2           | 催促メッセージが増える         |

### 4.3 シナリオで危険を許可する

同じ操作でも、状況によって正解になることがある。シナリオごとに危険の判定を上書きできるようにする。

```ts
dangerOverrides: {
  FORCE_PUSH_OVERWROTE: {
    allowIf: (ctx) => ctx.announcedInChat && ctx.usedForceWithLease,
    else: 'fatal',
  },
}
```

例：後輩が `.env` をpushしたシナリオ
- チャットで「履歴を書き換えるのでpullしないでください」と**周知し**、さらに `--force-with-lease` を使ったなら、force pushは許可する
- 周知せずに `--force` した場合は致命扱い

### 4.4 体験型と実戦型

|      | 体験型                                                                      | 実戦型                                         |
| ---- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| 目的 | **わざとやらかさせる**                                                      | 正しく対処させる                               |
| 流れ | 先輩「試しにmainへ直接pushしてみ？」→ やる → 上司が雷 → 解説 → 戻し方を練習 | 指示だけ出す。危険な操作をしたら普通に怒られる |
| 機嫌 | 減るが、雷になってもやり直しにはならない                                    | 雷になったら始末書をもらってやり直し           |
| 配置 | 序盤から中盤                                                                | 中盤から後半                                   |

## 5. 始末書図鑑（収集要素）

- 初めて起こした危険イベントごとに「始末書」が1枚手に入る
- 中身：
  - 何をしたか
  - なぜダメか
  - 正しい戻し方
  - 再発防止策（例：branch protection の設定、`.gitignore`、`--force-with-lease`）
  - 上司のひとこと
- 図鑑を**全部埋めることもやり込み要素**にする（「やってはいけないこと」を自分から体験したくなる）
- 始末書は**リスクの教科書**になる。これがアプリの学習価値の柱の1つ

## 6. git以外の行動（チャットで選ぶ）

- 実際の現場では、git以外の行動が正解のことがある。チャットに選択肢を出し、それも手数やゴール条件に含める
- 例：`.env` がpushされたとき、**最優先はAPIキーを無効にすること**。履歴を消しても、漏れたキーは取り消せない
  - → 選択肢「インフラ担当にキーの失効を依頼する」を選ばないと、Sランクは取れない
  - → 選ばずに履歴だけ消すと、上司に「履歴消しても漏れたキーは戻らん！」と言われる
- 他の選択肢：「チームに周知する」「先輩に相談する」「後輩に説明する」（説明すると後輩の信頼が上がる）

## 7. データ構造（シナリオの定義）

```ts
type Scenario = {
  id: string
  chapter: number
  mode: 'experience' | 'practice' // 体験型 or 実戦型
  cast: ('kouhai' | 'boss' | 'senpai')[]
  initialWorld: WorldSnapshot
  npcScript: NpcStep[] // いつ・誰が・どのコマンドを打つか
  deadlineSec?: number // 期限（実時間の秒数）
  clockStart?: string // 作中時計の開始時刻（例 '17:45'）
  clockScale?: number // 実時間1秒あたりに作中で進む秒数（標準は1）
  par: number
  goals: Predicate[] // すべて満たしたらクリア
  milestones: { id: string; when: Predicate; line?: string }[]
  smartMoves: { match: CommandPattern; line: string }[]
  dangerOverrides?: Record<DangerEvent, OverrideRule>
  chatChoices?: ChatChoice[] // git以外の行動
  assist: 'full' | 'basic' | 'observe-only' | 'none' // 補助チップの段階

  initialMood?: number

```

## 8. 時間の扱い

### 8.1 作中の時計と期限

- 作中の時計は**実時間で進む**。速さは `clockScale` で決める（標準は等倍）
  - 例：17:45 から始まり、18:00 の定時が迫ってくる
- そのうえで、コマンドやヒントの**所要時間**だけ時計が飛ぶ（2026-10-26 に採用。docs/06 の 2.2）
  - 作中の時刻 = 開始時刻 ＋ 実時間 × `clockScale` ＋ 所要時間の合計（`extraClockSec`）
  - 期限の判定も、所要時間を足した時刻で行う
  - 所要時間の目安（docs/04_spec_scenarios の 2.4）：見るだけのコマンド0分、ふつうのコマンド1分、エラー2分、ヒント5分
  - シナリオは `durationOf`（コマンドごと）と `hintSec`（ヒント）で上書きできる
  - 所要時間はコマンド列から決まるので、決定性とリプレイ（§8.3）は崩れない
  - 時計が飛んだときは `clock` の Cue を出し、画面は数字を0.6秒かけて早送りで回す
- 期限（`deadlineSec`）はヘッダーにカウントダウンで表示する
  - 残り30%で表示を強調する
  - 残り10%で上司からの催促が入る
- 期限を過ぎてもゲームオーバーにはしない。上司の機嫌が時間とともに減っていき（§4.2）、0になると雷になる
- 期限内に解決できないとSランクは取れない

### 8.2 手が止まったとき

- 最後の操作から**20秒**：後輩のアイコンに「…」が出る。減点はしない
- **45秒**から30秒ごと：信頼 −2。「（入力中…）」が出ては消える
- 序盤の章では、手が止まると先輩が助け舟を出す（ヒントの案内）。減点はしない
- 時間のかからない観測コマンドでも、考えている時間には時計が進む。「確認はタダ、迷いはタダではない」

### 8.3 決定性とリプレイ

- 演出エンジンへの入力は、`{ command, at: 経過ミリ秒 }` の列と、手が止まったことを知らせる `tick` イベント
- リプレイでは記録した `at` をそのまま使うので、同じ演出が再現される
- テストでは時刻を偽の時計で注入する

### 8.4 時間制限なしモード（設定）

- 設定でONにすると、時計を止め、期限と放置の減点をなくす
- ランクには「ゆっくり」の印をつける（Sランクの価値を保つため）
- 初回起動時に選ばせる（「時間制限あり（おすすめ）／なし」）

### 11.2 演出エンジンへの入力

演出エンジンへの入力（`DramaInput`）は次の6種類。`at` はシナリオ開始からの経過ミリ秒。

| 種類 | 中身 |
|---|---|
| `command` | コマンドの結果：終了コード、未対応か、意味イベント、状態のハッシュ、新たに満たしたマイルストーン、危険の信号、所要時間（`durationSec`） |
| `choice` | チャットで選んだ git 以外の行動（§6） |
| `hint` | ヒントを見た。所要時間（`durationSec`）だけ時計が飛ぶ |
| `note` | シナリオが決めた場面のセリフ（間違った解消への反応など）。信頼・機嫌の増減もつけられる |
| `tick` | 時間の経過。手が止まったときの反応と期限に使う。画面側が数秒ごとに送る |
| `finish` | ゴールを満たした。ランクを決める |

危険の判定は scenarios 層で行う。world を調べる必要があり、drama 層は engine の型にしか依存しない決まりだから。

判定する危険と、シナリオが決められる条件：

| 危険 | 判定の条件 |
|---|---|
| `SECRET_PUSHED` | 新しく送ったコミットに、`.env` などのファイルがある。調べるのは送り先のリポジトリ |
| `FORCE_PUSH_OVERWROTE` | force push で消えたコミットに、プレイヤー以外の作者がいる |
| `HISTORY_REWRITTEN_ON_SHARED_BRANCH` | force push で消えたのが、自分のコミットだけ |
| `DIRECT_PUSH_TO_PROTECTED` | シナリオが決めた保護ブランチに push した。既定はなし |
| `BAD_COMMIT_MESSAGE` | コミットメッセージの1行目が `修正` / `fix` / `aaa` などと一致した |
| `JUNK_STAGED` | `node_modules/` などを add した |

- 許可の判定（§4.3）は、シナリオが `allow(kind, command)` で行う。許可した危険は `allowed: true` で渡り、減点しない
- `UNCOMMITTED_CHANGES_DISCARDED` は、`reset --hard` などを実装する M5 で出せるようになる

### 11.3 Cue（演出側への出力）

§7 の案から、次のように決めた。演出側（別セッション）はこれを受け取って表示する。

| 種類 | 中身 |
|---|---|
| `chat` | `from`（kouhai / boss / senpai）、`key`（セリフの識別子）、`text`（仮の文）、`style`（normal / rage / whisper） |
| `face` | 後輩の表情の段階と、上がったか下がったか |
| `mood` | 上司の機嫌の段階 |
| `cutin` | rage / sparkle / despair / thunder |
| `shake` | 強さ 1〜3 |
| `typing` | 「入力中…」。`vanish` なら出ては消える |
| `report` | 始末書を初めて手に入れた。ヤバ度（`level`、Lv1〜5）つき |
| `clock` | 所要時間で作中の時計が飛んだ。飛んだ秒と、飛んだ秒の合計 |
| `deadline` | warning / urgent / over |
| `gauge` | 信頼と機嫌の今の値と増減（アニメーション用） |
| `rank` | ランクと「ゆっくり」の印 |

- セリフは key で識別する。演出側は、シナリオの `lines`（key → 候補）で差し替えられる
  - 同じ分類が続くとき（後退・エラー）は、後ろの候補ほどきつい言い方として段階的に使う
  - それ以外は、シードつきの乱数で選ぶ。直前と同じセリフは避ける

### 11.4 仕様からの補足・変更

- 「危険な操作の前に確認していた +3」は、許可された危険（周知してからの `--force-with-lease` など）にも当てはめる
- シミュレータの未対応のコマンドは、減点も手数もなしにする（学習者のせいではないので）
- 期限を過ぎた後の上司の催促は、機嫌が下がる3回に1回にする（チャットが埋まらないように）
- 後輩・上司がその場面にいない（cast にない）ときは、信頼・機嫌は動かず、セリフも出さない

### 12.2 流れ

1. 導入：3人のチャット、いまの状況（自分は切り捨ての修正をコミット済みで未 push、田中が先に料金改定を push した）、ゴール。「時間制限なし」を選べる
   - ゴールは2つ：「origin の main に、あなたの修正（端数の切り捨て）を届ける」「田中さんの修正（手数料率 3.6%）を消さない」
   - 遊んでいるあいだも、チャットの上にゴールを出す。origin の状態から判定して、その場でチェックがつく
   - 最初は田中さんの分だけ ✓。force push すると ✓ が入れ替わるので、押し切ると何を失うかが目で見える
   - 試遊で「何を達成すればいいかわからない」と言われたので足した（2026-10-26）
2. `git push` は拒否される（田中が先に calc.ts を push している）
3. `git pull` でコンフリクト。エディタに「自分の変更を採用」「取り込む変更を採用」が出る
   - どちらかを丸ごと採ると、もう片方の変更が消える。田中（`kouhai.lostRate` / `kouhai.lostFloor`）と、push 後に部長（`boss.lostFloorPushed`）が気づく
   - 正解は、手数料率 0.036（田中）と `Math.floor`（自分）の両方を残すこと
4. `git add` → `git commit` → `git push` でクリア。最短5手（par 5）

### 12.3 決めたこと

- 実戦型なので、致命的な危険（force push で他人のコミットを消した など）のあとは**チェックポイント**に戻れる
  - 戻るのは world だけ。始末書と機嫌・信頼の減りはそのまま（やらかした事実は消えない）
  - 戻ったときは先輩が `senpai.rollback` を言う
- 雷が落ちたら、チェックポイントか最初からやり直す（§4.1）。そのまま続けることもできる
- 作中15分（実時間5分、`clockScale` 3）しかないので、ヒントは標準の5分ではなく2分にした
- 補助チップに `--force` は出さない
- 場面のセリフ（`note`）は、同じものを1回しか言わない

### 12.4 間違えた後の救済（2026-10-26）

試遊で「コンフリクトの解消で修正を消したら詰む？」と聞かれた。直すコミットを足せば取り返せるが、それを教える手段がなかったので足した。

- シナリオは、いまの状態を12種類に見分ける（`phaseOf`）。ヒント・先輩の助け舟・補助チップは、これで出し分ける
  - 間違えた状態：片方の変更を消したまま解消（`conflictWrong`）、add（`mergeWrong`）、コミット・push（`committedWrong`）、直した後（`fixed`）、押し切った（`forced`）、ブランチから外れた（`detached`）
- **ヒント**（時間を払う。取り返し方まで言う）

| 状態 | 先輩が言うこと |
|---|---|
| 解消を間違えた | 両方を残すように直すか、`git merge --abort` で pull の前に戻る |
| add した後 | 直して、もう一回 add |
| コミット・push した後 | 直すコミットを足す（add → commit → push） |
| 直した後 | add → commit -m → push |
| 押し切った | チェックポイントか「やり直す」で戻る |
| ブランチから外れた | `git switch main` で戻る |

- **先輩の助け舟**（タダで出る。方向だけ）：間違えた状態なら「0.036 と Math.floor、両方ある？」のように、状態に合った声をかける
  - 演出エンジンの `tick` に `helperKey` を足した。シナリオが key を渡せば、`senpai.idle` の代わりにそれを言う
- 間違えたまま push したら、すぐに先輩が「直すコミットを足せばいい。慌てるな」と言う（押し切ったときは言わない）
- 画面の上に**「やり直す」**ボタンを足した。確認してから、同じ設定（時間制限の有無）で最初からやり直す
- **結末の出し分け**（演出案のセッションと決めた）：間違えて直したのは失敗ではなく、2番目に大事な学び（履歴は消さずに、直すコミットを足す）。だから悪い結末ではなく、少しちがう結末にする
  - 田中さんの 0.036 が消えたままコミットした（田中さんのコミットを取り込んだ後）→ 田中のお礼を `ending.thanksRecovered` に差し替える
  - 自分の Math.floor だけが消えていた → お礼はそのまま（田中さんの変更はずっと残っていたので、皮肉にならない）
  - どちらかで直してクリアした → 最後に先輩が `ending.recovered`（「消さずに、直すコミットを足す。それで合ってる」）
  - 始末書があるときは `ending.afterReport` を優先し、上の2つは出さない
  - ランクは手数のぶん自然に下がるだけで、別には減点しない（「直す」を罰しない）
  - 演出エンジンの `finish` に `replace`（結末のセリフの差し替え）と `epilogue`（最後に足すセリフ）を足した。シナリオは判定の結果を `StageEvaluation.ending` で渡す
- 戻すコマンド（`restore --merge`、`reset --hard ORIG_HEAD`）は、ほかの取り消し系と一緒に M5 で作る
